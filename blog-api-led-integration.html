Designing API-led integration that stays reusable

The three-layer model is useful only when API boundaries, ownership and governance reflect real business capabilities.

8 min readArchitecture guide

API-led connectivity is often introduced as three layers: System APIs, Process APIs and Experience APIs. The model becomes valuable when it reduces duplication, protects systems of record and gives product teams capabilities they can safely reuse. Simply labelling every endpoint does not create that outcome.

Give each layer one clear responsibility

System APIs

System APIs provide stable, governed access to systems such as Salesforce, SAP, databases and legacy platforms. They hide protocol and data-access complexity, but should avoid embedding channel-specific business behaviour.

Process APIs

Process APIs combine system capabilities into meaningful business operations. Customer onboarding, order fulfilment or member servicing are stronger boundaries than generic “orchestration” services because ownership and change impact are clearer.

Experience APIs

Experience APIs shape data and interactions for a specific channel or consumer—mobile, web, partner or internal application—without forcing source systems to understand presentation needs.

Design test:

If a second channel cannot reuse the underlying process without copying logic, the boundary probably needs refinement.

Treat contracts as products

A reusable API needs an owner, consumers, service levels, versioning policy and a lifecycle. Define contracts first using RAML or OpenAPI, agree error semantics and pagination, and include examples that show the intended consumer experience.

Apply security by design

  • Use OAuth 2.0 or OpenID Connect for consumer identity and authorisation.
  • Apply least privilege between runtime components and backend systems.
  • Use policies for rate limits, threat protection and token validation.
  • Keep secrets in a managed vault and use TLS for every network hop.
  • Classify sensitive fields and avoid logging customer data.

Know when an event is the better contract

REST APIs suit request-response interactions. Events suit state changes that multiple consumers may need, especially when producers should not wait for downstream work. A strong architecture commonly uses both: an API accepts a command and a durable event communicates the outcome.

Make governance part of delivery

Use reusable templates, automated checks, design reviews and a searchable catalogue. Measure reuse, reliability and lead time—not only the number of APIs published. Governance should make the right pattern easier to adopt.

A concise design checklist

  • Does the boundary represent a stable system or business capability?
  • Is the intended consumer and owner explicit?
  • Can the contract evolve without breaking consumers?
  • Are authentication, authorisation and data classification defined?
  • Are timeouts, retries, idempotency and failure paths documented?
  • Will logs, metrics and traces explain production behaviour?
